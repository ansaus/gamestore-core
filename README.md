# gamestore-core

Ядро магазина цифровых товаров: заказы, платёжные вебхуки, однократная автоматическая выдача.
Тестовое задание. Постановка — в [docs/TASK.md](docs/TASK.md).
Ключевые решения и почему они такие — в [NOTES.md](NOTES.md), фактическое время по этапам — в [TIME.md](TIME.md).

## Стек

| Компонент | Что это |
|---|---|
| PHP 8.3 + Laravel 12 | приложение |
| PostgreSQL 16 | единственный источник правды по идемпотентности |
| Redis | драйвер очередей |
| Docker Compose | `app`, `worker`, `scheduler`, `supplier-stub`, `nginx`, `postgres`, `redis` |
| Pest | тесты |

Магазин и заглушка поставщика — одна кодовая база, но **разные контейнеры**: так таймауты
поставщика ловятся честно, по сети. Какие роуты поднимать, решает `APP_ROLE`
(`app` | `stub` | `all`; `all` — только для тестов).

| URL | Что отвечает |
|---|---|
| http://localhost:8080 | REST API магазина |
| http://localhost:8090 | заглушка поставщика |

## Запуск

```bash
cp .env.example .env
sed -i "s/^UID=.*/UID=$(id -u)/; s/^GID=.*/GID=$(id -g)/" .env
make up          # поднять стек + миграции
make seed        # каталог и пул ключей
make test        # тесты
```

`UID`/`GID` в `.env` нужны, чтобы php-fpm внутри контейнера писал в примонтированный
`storage/` от имени хостового пользователя и не оставлял root-файлов в рабочей копии.

`queue:work` загружает код один раз при старте, поэтому после правок в `app/`
воркер надо перезапустить: `docker compose restart worker scheduler`. На php-fpm
(`app`, `supplier-stub`) это не распространяется — там каждый запрос свежий.

Без `make` те же шаги — напрямую:

```bash
docker compose up -d --build
docker compose exec -T app php artisan migrate --force
docker compose exec -T app php artisan db:seed --force
docker compose exec -T app php artisan test
```

## Быстрая проверка

```bash
# 1. создать заказ
curl -sX POST localhost:8080/api/orders \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -H 'Idempotency-Key: demo-1' \
  -d '{"sku":"KEY-CS2-PRIME"}'
# -> 201 {"id":"ord_00001","amount":"1290.00","status":"created",...}
#    повтор с тем же Idempotency-Key -> 200 и тот же заказ

# 2. оплата
curl -sX POST localhost:8080/api/webhooks/payment \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d '{"event_id":"evt_1","order_id":"ord_00001","status":"paid",
       "amount":1290,"currency":"RUB","created_at":"2026-09-02T12:00:00Z"}'
# -> 200 {"result":"applied"}      повтор того же event_id -> {"result":"duplicate"}

# 3. заказ с кодом (выдача асинхронная, ~секунда)
curl -s localhost:8080/api/orders/ord_00001 -H 'Accept: application/json'
# -> {"status":"delivered","delivery":{"code":"LFXC-TNCS-BPCD","supplier":"A",...}}
```

## API

| Метод | Путь | Ответы |
|---|---|---|
| `POST` | `/api/orders` | `201` создан, `200` повтор по `Idempotency-Key`, `404` нет sku, `409` sku неактивен |
| `GET` | `/api/orders/{id}` | `200` заказ с `delivery` и `timeline`, `404` |
| `POST` | `/api/webhooks/payment` | `200` принято или дубль, `400` невалидный payload, `5xx` сбой БД |
| `GET` | `/api/catalog` | `200` страница витрины с остатками |
| `GET` | `/api/admin/reconcile` | `200` отчёт сверки |
| `POST` | `/api/admin/orders/{id}/retry-delivery` | `200` поставлено в очередь, `404` нет заказа, `409` уже выдан или не оплачен |
| `POST` | `/api/admin/stock/{sku}/refill` | `200` пополнено, `404` нет sku, `422` некорректное `quantity` |

Авторизации у `/api/admin/*` нет по условию задания; в бою префикс
закрывается на ingress.

Тело `GET /api/orders/{id}` — надмножество ответа на создание: одна и та же
структура на оба эндпоинта. Деньги отдаются строкой (`"1290.00"`), чтобы клиент
не превратил их во float.

`POST /api/orders` может вернуть заказ сразу в статусе `paid` или `payment_failed`:
если оплата пришла раньше заказа, она применяется в той же транзакции, что и вставка
(см. «Событие раньше заказа» ниже).

`timeline` собирается из отметок времени самого заказа — отдельной таблицы истории
в схеме нет. Статусы без своей колонки (`delivering`, `out_of_stock`, …)
показываются одной точкой по `updated_at`.

Возможные `result` вебхука:

| result | Когда |
|---|---|
| `applied` | событие изменило статус заказа |
| `duplicate` | такой `event_id` уже принимали |
| `orphan` | заказа ещё нет; событие сохранено и будет применено, когда заказ появится |
| `stale` | `failed` после подтверждённой оплаты — статус не откатываем |
| `ignored_terminal` | заказ уже в этом или более позднем состоянии |

## Exactly-once под гонками

### Один заказ, много вебхуков

Дедупликация держится на одной операции: `INSERT INTO payment_events ... ON CONFLICT
(event_id) DO NOTHING`. Не «проверить SELECT'ом и вставить» — между проверкой и вставкой
пролезает второй запрос. Дальше `SELECT ... FOR UPDATE` по строке заказа выстраивает
параллельные обработчики в очередь, а сам переход статуса — условный
`UPDATE ... WHERE status IN (...)`: нулевой rowcount означает не ошибку, а проигранную
гонку.

Три уровня защиты, и последний — в БД: даже если прогорят первые два,
`deliveries.order_id` PRIMARY KEY не даст создать вторую выдачу.

### Событие раньше заказа

Вебхук по неизвестному `order_id` не отвергается (`404` заставил бы платёжку долбиться
повторами) и не теряется: он ложится в `payment_events` с `applied_at = null` и
`apply_result = 'orphan'`. Подхват — в двух местах:

1. **при создании заказа** — в той же транзакции, что и вставка. Наружу заказ не может
   появиться без применённых к нему событий, поэтому `POST /api/orders` возвращает сразу
   `paid`, а не `created`, который через миг станет `paid`;
2. **фоновой задачей** `ReconcileOrphanEvents` раз в минуту — на случай, если заказ
   появился мимо API. Механизм внутри тот же самый (`applyPending`), поэтому пересечение
   двух подхватов безопасно.

Накопленные события применяются в порядке `occurred_at` из payload, при равенстве — по
`received_at`. Событие без `occurred_at` считается случившимся тогда, когда мы его
получили: другой отметки времени про него у нас нет.

Событие по заказу, которого нет и не будет, фоновая задача не перебирает (join с `orders`
её отсекает) — место такой сироты в отчёте сверки, а не в очереди на применение.

### Сценарии гонки

`scripts/race.php` бьёт по **настоящему HTTP** через nginx в поднятый стек с живым
воркером. Внутрипроцессный тест здесь бесполезен: гонку создают параллельные php-fpm
воркеры, борющиеся за одну строку в Postgres. Все curl-хендлы добавляются в multi-хендл
до первого `curl_multi_exec()` — старт по общему барьеру.

```bash
make scenario-race         # 1:  50 вебхуков, разные event_id
make scenario-race-dup     # 1b: 50 вебхуков, один и тот же event_id
make scenario-race-mixed   # 3:  paid, дубли и опоздавшие failed вперемешку
make race                  # все три подряд

# параметры: N=200 MODE=mixed SKU=... ORDER=ord_00042
```

Скрипт сам печатает вердикт по каждому инварианту и возвращает ненулевой код при
нарушении — годится в CI как есть.

```
  Отстрелялись за 544 мс. HTTP: 200×50
  Ответы вебхука: applied×1, duplicate×49

  [  OK  ] Все ответы 200  — 50
  [  OK  ] Строк в deliveries  — 1
  [  OK  ] Итоговый статус заказа  — delivered
  [  OK  ] Проводок оплаты (одна пара)  — 2
  [  OK  ] Журнал по заказу сходится  — debit=2193.00 credit=2193.00
  [  OK  ] Событий оплаты применено  — 1
  ...
  ИНВАРИАНТЫ ЦЕЛЫ
```

Если пул ключей поставщика A пуст, скрипт останавливается до залпа и говорит об этом:
выдавать заказ было бы нечем, и вердикт получился бы ложным. Сброс — `make stub-reset`.

## Заглушка поставщика

```bash
# детерминированное поведение для сценариев
curl -sX POST localhost:8090/stub/config -H 'Content-Type: application/json' \
  -d '{"supplier":"A","force":"out_of_stock"}'
#   force: none | timeout_after_issue | http_500 | out_of_stock
#   плюс fail_rate, timeout_rate, latency_ms, timeout_sleep_ms

curl -s  localhost:8090/stub/state      # остатки пула, выданные ключи, счётчики
curl -sX POST localhost:8090/stub/reset # вернуть пул в исходное состояние
```

Сброс пула (`make stub-reset`) освобождает **все** ключи, включая уже проданные,
поэтому его нельзя делать в отрыве от домена: поставщик начнёт выдавать коды,
которые в `deliveries` уже есть. Продать их второй раз не даст `deliveries.code`
UNIQUE (I2) — заказ уйдёт в `unclaimed_codes` с `code_already_sold`. Сбрасывать
надо вместе: `make fresh`. Скрипты сценариев поэтому пул не трогают вообще, а
только проверяют, что свободные ключи ещё остались.

Пул из `docs/keys.json` делится фиксированно: первые 30 ключей → поставщик A,
последние 20 → B. Случайное деление сделало бы сценарии `out_of_stock` и фолбэка
невоспроизводимыми.

Заглушка **сначала фиксирует выдачу в БД и только потом «зависает»** — иначе
сценарий «таймаут, но код уже выдан» не воспроизводится. Повтор с тем же
`request_id` всегда возвращает тот же код и не тратит второй ключ.

## Устойчивость к поставщику

### Таймаут ≠ отказ

Ответ поставщика делится на три класса, и разница между вторым и третьим —
самое важное место в проекте:

| Ответ | Класс | Что делаем |
|---|---|---|
| `200` + code | успех | сохраняем код, `state='succeeded'` |
| `409 out_of_stock`, любой `4xx` | **определённый отказ** | `state='failed'`, можно к следующему поставщику |
| `5xx` | **неопределённость** | `state='unknown'`, ретрай ТЕМ ЖЕ `request_id` |
| таймаут, обрыв сети | **неопределённость** | `state='unknown'`, ретрай ТЕМ ЖЕ `request_id` |

Таймаут не говорит «ключ не выдан». Он говорит «я не знаю». Поставщик мог
зафиксировать выдачу и не успеть ответить — именно это и воспроизводит
`force=timeout_after_issue`.

### Почему `request_id` детерминирован

`req_{order_id}_{supplier}` вычисляется из заказа и поставщика и **не меняется
между попытками**. Это единственный способ выполнить требование «повтор после
таймаута не создаёт вторую выдачу»: повтор работает как probe — он либо вернёт
код, выданный на первой попытке, либо выдаст новый, но никогда не выдаст второй.
Со стороны заглушки это закрыто `stub_issues.request_id` PRIMARY KEY (I4).

Клиент делает до 3 попыток на поставщика с бэкоффом `200ms * 2^n` и джиттером
±30%. Джиттер не украшение: без него все заказы, упавшие в одну секунду, пойдут
на ретрай одной волной и добьют поставщика, который только начал подниматься.

### Когда фолбэк A→B разрешён

Только при **определённом** отказе A:

- A вернул `out_of_stock` или другой `4xx` → сразу к B, у B свой `request_id`;
- A был `unknown`, но ретрай прояснил исход → действуем по прояснённому;
- A остался `unknown` после 3 попыток → **к B не идём**. Заказ остаётся в
  `delivering`, получает `next_attempt_at = now() + 30s` и ждёт следующего цикла.

Последний пункт — осознанный выбор: лучше задержать выдачу, чем задвоить.
Уход к B из состояния `unknown` списал бы два ключа за один заказ. Терпение не
бесконечно: после `SUPPLIER_MAX_DELIVERY_CYCLES` циклов заказ уходит в
`delivery_failed` — состояние восстановимое, но уже с `level=error` в логах.

Отдельный случай — поставщик вернул код, уже проданный другому заказу. Продать
один ключ дважды не даёт `deliveries.code` UNIQUE (I2); мы не падаем на этом
ограничении, а паркуем код в `unclaimed_codes` с причиной `code_already_sold`
и орём в лог.

Крутится всё это конфигом:

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `SUPPLIER_CONNECT_TIMEOUT` / `SUPPLIER_TIMEOUT` | `1` / `2` | таймауты соединения и ответа, секунды |
| `SUPPLIER_MAX_ATTEMPTS` | `3` | попыток к одному поставщику за цикл |
| `SUPPLIER_BACKOFF_MS` | `200` | база бэкоффа между попытками |
| `SUPPLIER_UNKNOWN_RETRY_DELAY` | `30` | пауза до следующего цикла, секунды |
| `SUPPLIER_MAX_DELIVERY_CYCLES` | `5` | циклов до `delivery_failed` |

```bash
make scenario-timeout    # 4: A «завис» ПОСЛЕ выдачи — один ключ, тот же код
make scenario-fallback   # 5: A отказал определённо — выдача от B
```

Каждый печатает вердикт по пунктам и возвращает ненулевой код при нарушении.

## Витрина под нагрузкой

### Запрос

```
GET /api/catalog?type=key&after=BULK-002532&limit=50

{ "items": [{sku, name, type, price, currency, image, available}, ...],
  "next_cursor": "BULK-002582" | null,
  "limit": 50 }
```

`next_cursor` — это `sku` последней строки страницы; его же передают в `after`.
`null` означает, что страница последняя. Чтобы это узнать, витрина берёт из БД на
одну строку больше запрошенного, а не считает `count(*)` по всему каталогу.

### Три решения и что они дают

Датасет: **5 000 SKU, 500 000 ключей** (`make seed SCALE=big`), замеры —
`make bench`, вывод ниже настоящий.

**1. Остаток из счётчика, а не агрегатом по пулу ключей.** `product_stock`
обновляется в той же транзакции, что и выдача, — витрина читает готовое число.

```
ДО — count(*) по пулу ключей на каждый SKU        медиана 315.7 мс
  Limit  (actual time=424.797..424.808 rows=50 loops=1)
    Buffers: shared hit=5056 read=163
    ->  Sort (Sort Method: top-N heapsort  Memory: 36kB)
          ->  HashAggregate  (actual time=421.677..423.211 rows=4962 loops=1)
                ->  Hash Right Join  (actual time=3.724..290.881 rows=495012 loops=1)
                      ->  Seq Scan on stub_keys k  (actual time=0.012..110.103 rows=500043)
                            Filter: (status = 'free'::text)
  Execution Time: 425.412 ms

ПОСЛЕ — чтение product_stock                        медиана 1.9 мс
  Limit  (actual time=0.042..0.089 rows=50 loops=1)
    Buffers: shared hit=6
    ->  Merge Join  (actual time=0.042..0.083 rows=50 loops=1)
          Merge Cond: (p.sku = s.sku)
          ->  Index Scan using products_active_sku_idx on products p  (rows=50)
          ->  Index Scan using product_stock_pkey on product_stock s  (rows=50)
  Execution Time: 0.281 ms
```

Читается план так: наивный вариант обязан пройти **весь** пул (`Seq Scan`,
500 043 строки, 110 мс только на чтение), сложить его в хеш-таблицу и
сгруппировать — и лишь потом отдать 50 строк. Стоимость витрины растёт вместе с
пулом ключей, к которому витрина отношения не имеет. Счётчик превращает это в
`Merge Join` двух индексов по первичным ключам: **6 буферов вместо 5 219**,
и прочитано ровно 50 строк — столько, сколько отдано.

**2. Keyset вместо OFFSET.**

```
ДО — OFFSET 2506                                    Execution Time: 2.420 ms
  ->  Index Only Scan ... on products p  (actual rows=2556)   ← прочитано 2556
ПОСЛЕ — where sku > 'BULK-002532'                   Execution Time: 1.002 ms
  ->  Index Only Scan ... on products p  (actual rows=50)     ← прочитано 50
        Index Cond: (sku > 'BULK-002532'::text)
```

Абсолютная разница на 5 000 SKU невелика — и это честно: интересна не она, а
число прочитанных строк. `OFFSET` прочитал 2 556 строк, чтобы отдать 50, и на
странице №1000 прочитал бы 50 050. Keyset читает 50 на любой странице: индекс
позиционируется сразу по `Index Cond`.

**3. Частичные индексы.** `products(type, sku) where is_active` покрывает и
фильтр, и сортировку сразу:

```
->  Index Only Scan using products_active_type_sku_idx on products p  (rows=50)
      Index Cond: ((type = 'key'::text) AND (sku > 'BULK-002532'::text))
      Heap Fetches: 0
```

`Index Only Scan` с `Heap Fetches: 0` означает, что до самой таблицы дело не
дошло. Второй индекс, `products(sku) where is_active`, делает то же для витрины
без фильтра: по первичному ключу это тоже `Index Scan`, но с проверкой
`is_active` на каждой строке — частичный индекс убирает и её.

### Кеш

Страница кешируется в Redis на `CATALOG_CACHE_TTL` секунд. Инвалидация — сменой
номера версии в ключе (`catalog:v7:<хеш параметров>`), а не перебором ключей:
страниц у витрины много (типы × курсоры × лимиты), обойти их все на каждой выдаче
дороже, чем сменить одно число. Версия растёт при выдаче и при пополнении
остатка; старые записи никто больше не спросит, и они истекают сами.

Остаток на витрине заведомо чуть устаревший, и это безопасно: точная правда
проверяется в момент выдачи, а расхождение приводит к восстановимому
`out_of_stock`, а не к продаже воздуха.

### Ключ привязан к товару

Этап 5 добавил `stub_keys.sku`: без него вопрос «сколько ключей есть по этому
SKU» не задать, а именно он и есть наивная альтернатива счётчику. Колонка
nullable, `NULL` — «универсальный ключ». Демо-пул из `docs/keys.json` остаётся
весь в `NULL`, поэтому сценарии 1–6 работают ровно как раньше; нагрузочный пул
привязан к товарам, по 100 ключей на SKU.

Занятие ключа при выдаче идёт `FOR UPDATE SKIP LOCKED` по частичному индексу
`(supplier, sku, id) where status = 'free'`: при сотне параллельных покупок
одного SKU воркеры не встают в очередь на одну строку, а разбирают разные.

```bash
make seed SCALE=big   # 5 000 SKU, 500 000 ключей
make bench            # EXPLAIN (ANALYZE, BUFFERS) по всем трём парам
```

## Сверка и восстановление

### `GET /api/admin/reconcile`

Отчёт отвечает на один вопрос: есть ли сейчас в системе деньги или коды,
оказавшиеся не там, где должны. Поэтому каждая секция — список находок, а не
счётчик, и `healthy` равен «все секции пусты и журнал сходится».

| Секция | Что означает |
|---|---|
| `paid_not_delivered` | деньги пришли, товар не ушёл — главная секция |
| `delivered_not_paid` | товар ушёл без денег; всегда пуста, но проверяется, а не декларируется |
| `orphan_events` | события, не применённые ни к одному заказу |
| `stuck_in_delivering` | заказы, зависшие в выдаче |
| `unknown_supplier_requests` | заявки, по которым неизвестно, выдал ли поставщик код |
| `unclaimed_codes` | коды, за которые заплачено, но заказу они не нужны |
| `amount_mismatch_events` | платёжка прислала не ту сумму |
| `unbalanced_orders` | заказы, по которым дебет ≠ кредит |
| `ledger` | `debit`, `credit`, `balanced` — инвариант I6 |

Свежие расхождения находками не считаются: заказ, оплаченный секунду назад и ещё
не выданный, — это нормальная асинхронность. Порог задаёт `RECONCILE_GRACE_SECONDS`.

Две последние секции нужны отдельного упоминания. `unknown_supplier_requests` и
`unclaimed_codes` — единственное место, где эти сущности вообще видны: заказ может
быть давно закрыт другим поставщиком, а зависшая заявка и оплаченный чужой код
останутся молча лежать в БД. Без отчёта о них никто не узнает.

`unbalanced_orders` — это I6 в разрезе заказа. Глобальный ноль легко получить из
двух ошибок, компенсирующих друг друга на разных заказах, поэтому баланс
проверяется в двух разрезах сразу. Сравнение идёт через `bccomp` по строкам:
`numeric(12,2)`, загнанный в float, — ровно тот способ потерять копейку, от
которого весь проект и защищается.

Тот же отчёт в консоли, с ненулевым кодом возврата при находках:

```bash
make reconcile                                  # таблицами
docker compose exec -T app php artisan reconcile:report --json
```

### Фоновое доведение

`ReconcileStuckOrders` раз в минуту находит оплаченные, но не выданные заказы и
прогоняет их через ту же `DeliverOrderJob` с теми же `request_id` и теми же
проверками. Ничего «умного»: повторный запуск для уже выданного заказа — штатный
no-op, на этом и стоит безопасность всей затеи.

- берёт `paid`, `out_of_stock`, `delivery_failed`, а `delivering` — только
  состарившийся: свежий это заказ, которым прямо сейчас занят воркер;
- заказ без `next_attempt_at` подхватывается сразу — так возвращаются те, чья
  джоба потерялась вместе с упавшим воркером;
- перед отправкой в очередь двигает `next_attempt_at` вперёд. Это лизинг, а не
  косметика: иначе следующий тик заберёт заказ, пока предыдущая джоба ещё в очереди;
- бэкофф экспоненциальный по числу циклов, до `RECONCILE_MAX_BACKOFF`;
- после `RECONCILE_MAX_ATTEMPTS` циклов заказ остаётся человеку — бесконечно
  долбиться в поставщика бессмысленно.

### Ручное вмешательство

```bash
# довести заказ сейчас, не дожидаясь бэкоффа (обнуляет счётчик циклов)
curl -sX POST localhost:8080/api/admin/orders/ord_00001/retry-delivery

# пополнить витрину и разбудить заказы, ушедшие в out_of_stock по этому sku
curl -sX POST localhost:8080/api/admin/stock/KEY-CS2-PRIME/refill \
  -H 'Content-Type: application/json' -d '{"quantity":50}'
```

Витрина — денормализованный счётчик, а не источник правды: настоящие ключи лежат
у поставщика. Поэтому `refill` поднимает счётчик и сбрасывает бэкофф ждущим
заказам, а дальше их забирает обычное фоновое доведение.

```bash
make scenario-oos   # 6: пустой пул → out_of_stock → пополнение → delivered
```

### Логи

Одна строка JSON на событие в stdout, обязательные поля — на верхнем
уровне, а не внутри `context`. Вся история одного заказа достаётся так:

```bash
docker compose logs worker | jq -c 'select(.order_id == "ord_00042")'
```

```json
{"ts":"...","level":"info","event":"supplier.call","order_id":"ord_00042",
 "request_id":"req_ord_00042_A","supplier":"A","attempt":2,"outcome":"succeeded",
 "duration_ms":48,"channel":"local","context":{"http_status":200}}
```

Ключи с `null` не печатаются: в строке про платёж нет `supplier`, и место под него
занимать незачем.

## Инварианты в БД

Каждый пункт закрыт ограничением, а не только кодом:

| # | Инвариант | Чем закрыт |
|---|---|---|
| I1 | не больше одной выдачи на заказ | `deliveries.order_id` PRIMARY KEY |
| I2 | один код не уйдёт в два заказа | `deliveries.code` UNIQUE + `stub.stub_keys.code` UNIQUE |
| I3 | `event_id` применяется один раз | `payment_events.event_id` PK + `INSERT ... ON CONFLICT DO NOTHING` |
| I4 | повтор `request_id` → тот же код | `stub.stub_issues.request_id` PRIMARY KEY |
| I5 | финальный статус не откатывается | условный `UPDATE ... WHERE status IN (...)` + проверка rowcount |
| I6 | журнал денег сходится | двойная запись + `unique (ref_type, ref_id, account, direction)` |
| I7 | HTTP не внутри транзакции БД | вызов поставщика вынесен между двумя транзакциями |

Заглушка живёт в отдельной схеме Postgres `stub` — её состояние не смешивается с доменом.

## Тесты

Тесты гоняются по **PostgreSQL** (отдельная БД `gamestore_test`, создаётся при первом
подъёме `postgres`), а не по sqlite: инварианты держатся на частичных индексах, `jsonb`,
`numeric` и `FOR UPDATE SKIP LOCKED` — на sqlite это не проверяется.

HTTP к поставщику в тестах не уходит в сеть: транспорт подменяется, но логика заглушки
остаётся настоящей — тот же `StubIssuer` и та же БД. Настоящий сетевой прогон — в
сценариях приёмки (`make race` и далее).

Что уже есть за пределами минимума этапа 1 и почему:

- **вся схема БД сразу**, включая `supplier_requests`, `unclaimed_codes` и
  `ledger_entries` — схема оценивается как целое, а дробить её по этапам означало бы
  переписывать миграции на каждом шаге;
- **журнал денежных движений** — проводки пишутся в тех же транзакциях, что применение
  платежа и выдача. Добавлять их позже значило бы переоткрывать и перепроверять обе;
- **заглушка целиком**, вместе с `force`-режимами — без неё этап 1 нечем довести до
  `delivered`, а `force` нужен, чтобы тесты не флакали на `mt_rand`;
- **структурные JSON-логи в stdout** — канал `json` уже был прописан в `.env.example`.

Ключевые решения вынесены в [NOTES.md](NOTES.md) — там же три находки, вылезшие
не при написании, а на живых прогонах.
